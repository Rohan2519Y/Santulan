## Global rules for every task (from the constitution)

- **No relational code in new files.** PostgreSQL code is left untouched until US7 deletes it; nothing new may import `pg`.
- **Only `backend/src/modules/santulan/store/` imports `mongodb` or calls `.collection(`** (guarantee G-27). Everything else uses repositories obtained from `withScope(...)`.
- **Two credentials.** Application code and every test *under test* use the **runtime** credential (`santulan_runtime`). Fixtures, cleanup, migrations, scripts and the backup drill use the **migrator** credential (`santulan_migrator`), never present in the API process environment.
- **No `remove` anywhere for the runtime credential.** Retire by status; supersede by new revision/decision; tests clean up through the migrator.
- **Tier A** collections (`audit_logs`, `score_results`, `response_events`, `items`, `participant_cohort_history`, `growth_reviews`, `pathway_decisions`, `pathway_reviews`) are insert-only for the runtime credential; **Tier B** collections expose only their named mutation (data-model §2).
- Every multi-step action is **one transaction** (`snapshot` read concern, `majority` write concern); state moves are **compare-and-set** (`updateOne({_id, status: <from>}, …)`); the audit insert is inside the same transaction and its failure aborts it.
- No PII field; no client-supplied score, version, Santulan ID, participant id or store scope; unknown request keys are `400 VALIDATION_ERROR`; no prohibited claim in any string.
- A value the contracts do not state is marked `ASSUMED (D-11)` in code and in the data model.
- Migrations are forward-only; an applied migration is never edited (a fix is a new numbered file).
- Record staging-only checks as `NOT_EXECUTED` in the evidence register; never mark them PASS.

- Foundational: the 15 test files are independent [P]; the six `db/schema/collections/*.js` files, `views.js`, `roles.js`, `store/errors.js`, `store/transactions.js`, the audit and idempotency ports are independent [P]; `indexes.js`, migrations, `db-migrate.js` follow the schema files.
- US1 and US2 can proceed in parallel after Phase 2 (different modules); within each, all test files are [P].
- US8: the scoring, quality, evidence, release-flag, report, growth and pathway **test files** are all [P]; growth/pathway/worker/frontend implementation tasks are [P] once the store repositories exist.
- US5: services (`controlService`, `institutionService`, `participantAdminService`, `monitoringService`) are [P]; the seven admin pages are [P].
- US6: the five security test files are [P]; drill, manifest and launch-gate register are [P].
- Different developers can take US2/US4 (question sets), US1 (identity ports) and, after Phase 2, the frontend option player while the backend delivery port proceeds.

## Implementation Strategy

### MVP first (Phases 1–4)

1. Setup → Foundational → **US1** (identity/consent on MongoDB) → **US2** (spreadsheet upload into draft sets).
2. STOP and validate with quickstart §1–§5: the smallest slice that proves the store guarantees, the scoped access layer, and the owner's headline capability (upload the sample file).

### Incremental delivery

3. **US4** freeze/open → quickstart §6. 4. **US3** variable-option delivery → §7. 5. **US8** scoring and reports → §7b (the pipeline is now end-to-end).
6. **US5** admin/research → §9, **US6** security/QA → §10, **US7** removal and documentation → §11–§12.
7. Launch stays **NO-GO** until the evidence register shows real PASS entries for the staging-only items and the governance gates in the launch-gate register are closed by their owners.

### Guardrails while executing

- Stop and raise a change record if a contract detail is missing or ambiguous (constitution I); do not guess. The decisions D-M01…D-M17 are defaults applied pending owner confirmation.
- Never import the driver outside `store/`, never use the migrator credential in application code, never give the runtime credential `remove`, and never edit an applied data-model migration.
- Do not mark a task done while its test is skipped, unless the skip is the documented staging-only or `RUN_LOAD` case.
- Evidence from the PostgreSQL run does not count: every matrix ID passes again on MongoDB before it is registered as PASS.
